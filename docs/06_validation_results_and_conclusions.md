# 真实验证结果与结论

## 1. 这个项目解决什么

项目服务数据分析、增长分析、商业分析和电商运营分析岗位，沿“线索获取 → 商家成交 → 商家经营 → 订单履约 → 用户体验”建立可追溯的数据、预测和运营决策链路。它回答渠道是否不仅能成交还能带来有价值的商家，哪些商家/订单应先做履约治理，以及哪些品类更值得获得近期运营资源。

## 2. 数据与实现

本地使用 11 个 Olist 官方匿名公开 CSV，解压后约 121 MB，包含 8,000 条 MQL、842 条成交记录、99,441 笔订单、112,650 条订单商品、99,224 条评价和 3,095 个商家。数据时间主要覆盖 2016–2018 年。

实现包括：

- DuckDB + dbt 的 staging、intermediate、mart 三层数据仓库，共 29 个模型；
- 漏斗、渠道质量、商家经营、30/60/90 天窗口、履约体验、商家风险和需求资源分层；
- 线索成交排序、订单低评分风险排序、商家/品类周度需求回测；
- 统一商家运营行动清单、实验登记/随机分组/日志契约、10 页 Streamlit 看板、可下载清单和公开历史数据下的容量情景模拟。

## 3. 验证和真实问题

最终验证环境是 Python 3.12.13、dbt-core 1.12.0、dbt-duckdb 1.10.1、DuckDB 1.5.5、scikit-learn 1.9.0 和 Streamlit 1.60.0。P13 终验时 64 个 Python 测试全部通过；dbt 运行 86 个节点，84 通过、2 告警、0 错误。

真实数据暴露出的问题包括：1 条成交早于首次接触、189 条订单时间顺序异常、547 个订单有多条评价、1,603 条订单商品无有效品类、需求数据最后两周不完整，以及商家级周序列高度稀疏。这些问题都被保留、标记或按可追溯规则处理，没有为追求指标而静默删除。

## 4. 业务结论

- 8,000 条 MQL 中有 841 条合法成交，成交率 10.51%。`organic_search` 具有 2,296 条 MQL、11.76% 成交率，且成交商家后续延迟率 4.87%、低评分率 9.52%，是相对稳定的参照渠道。
- `unknown` 的成交率高达 16.65%，但无法精确归因，且成交商家延迟率 9.09%、低评分率 14.35%。结论是先修复来源追踪，而不是直接扩量。
- 样本已交付 GMV 为 1,541.98 万，延迟率 8.11%，低评分率 14.19%。199 个高价值高风险商家覆盖 405.95 万 GMV，约占 26.33%，适合作为优先治理清单。
- MA、CE、BA、RJ 等客户州出现高延迟热点；`moveis_escritorio` 的低评分率为 22.48%（n=1,259）。这些是调查线索，不是地区或品类导致结果的因果证明。

## 5. 模型结论

- 线索随机森林在 2,899 条时间外测试样本上的 PR-AUC 为 0.193，基线为 0.119；Top 20% 精准率 21.03%、覆盖率 35.36%、Lift 1.77。
- P8 低评分选模期逻辑回归 PR-AUC 0.341，高于随机森林 0.328，因此选择逻辑回归。其 26,016 条测试样本 PR-AUC 为 0.197（95% 区间 0.186–0.211），基线为 0.110；Top 10% Lift 2.32，Top 20% Lift 1.72。独立时间校准后 Brier 为 0.097，略优于先验基线 0.099。
- 低评分滚动 3 窗 PR-AUC均值为逻辑回归 0.243、随机森林 0.242；随机森林仅 1/3 窗胜出。相对首轮是 PR-AUC、Top 10% 和校准局部改善，但 Top 20% Lift 没有超过首轮 1.77，不称全面提升。
- 需求模型截点为 2018-08-20。品类 HistGradientBoosting WAPE 31.31%，略优于 4 周移动平均 32.68%。P9 商家活动分类器在 23,268 个时间外商家周上的 PR-AUC 为 0.680，Brier 为 0.111，8/8 周都高于当周活动率；两阶段期望订单量 WAPE 为 84.46%，相对移动平均 86.95% 有限改善，8 周中 7 周不劣。
- 商家结果仍不能称准确预测：长尾/沉默、间歇活跃、持续活跃三层 WAPE 分别为 129.68%、122.99% 和 63.14%；间歇层还弱于移动平均 120.88%。因此商家侧主价值是活动优先级，订单量只作辅助，品类仍承担总量规划。
- P10 将风险 mart 与 P9 商家资源计划一对一连接，3,095 个风险商家中 3,051 个具有活动分数，覆盖 98.58%；另 44 个不补造概率，继续保留在风险页。行动清单包含 158 个 P1 履约护航、178 个 P2 增长承接、55 个 P3 风险巡检、173 个 P4 重点经营和 2,487 个 P5 常规观察商家。
- 在默认 200 个离线排期名额下，统一规则覆盖 79.40% 的可评分高价值高风险商家，显著高于只按活动概率的 22.61% 和只按近期 GMV 的 26.63%；代价是活动概率质量覆盖为 20.20%，低于只按活动概率的 28.14%，近期 GMV覆盖为 34.61%，低于只按 GMV 的 60.75%。因此统一规则适合风险保护目标，不是所有目标的全局最优排序。
- P11 用真实 P1 候选池验证实验可行性：158 个单周候选在基线 14.19%、目标降低 3 个百分点、alpha 0.05、power 80%和 50/50 分流假设下，远少于 3,864 个规划成熟样本；当前池近似只能识别 12.10 个百分点下降。稳定哈希草案分为处理组 82、对照组 76，但这不是实验启动或效果结果。

## 6. 局限与下一步

数据是 2016–2018 年的公开匿名样本，缺少渠道成本、毛利、库存、承运商和真实干预日志；未评价订单不进入低评分标签，可能存在选择偏差。因此不计算 ROI，不声称线上提升或业务收益。P11 已提供空日志契约和随机实验设计，但真实运营仍需标准化动作、跨周滚动入组、等待结果成熟并按 ITT 分析后，才能评估增量。

详细口径见 `01_requirements_and_metrics.md`和 `metric_dictionary.md`，数据边界见 `03_data_design.md`，实验边界见 `07_intervention_and_experiment_design.md`，基础真实构建见 `logs/2026-07-30_real_data_validation.md`，P9 两阶段模型见 `logs/2026-08-01_p9_intermittent_demand_development.md`，P10 行动决策层见 `logs/2026-08-01_p10_seller_ops_actioning.md`，P11 实验框架见 `logs/2026-08-01_p11_intervention_experiment_framework.md`。

## 7. P12 投递验收结论

P12 没有训练新模型，也没有新增业务效果数字。它把当前权威产物生成成 `portfolio_evidence.json`、案例报告和原生可视化报告，并用自动检查防止后续重跑后材料仍引用旧数字。快速验收实际检查了 5 条简历 bullet、20 个面试问题、0 个无效内部链接、4 张 1440×1000 PNG，以及作品集证据和 10 页看板；17 项专项测试通过。全量 62 项 Python 测试与 dbt 回归也通过，dbt 两条历史数据告警保持不变。

截图阶段真实发现并修复了 Streamlit 入口遮蔽 `app` 包、导入缓存导致新会话不渲染的问题。最终使用根目录 `streamlit_app.py` 调用显式 `main()`，四张截图均由修复后的本地服务生成并目视确认。原生报告在渲染前通过结构校验，包含 4 个有界数据集、3 类来源、2 张原生图和 1 张模型对照表。详细过程见 `logs/2026-08-02_p12_portfolio_delivery.md`。

## 8. P13 发布、视觉和岗位材料验收结论

P13 没有重新训练模型，也没有新增业务效果数字。仓库增加 Python 3.12 GitHub Actions、只读 `contents` 权限、pip 缓存、PR/Issue 模板、贡献规范、发布清单和机器可执行仓库检查。作品集测试改为读取版本化证据，因此无原始 CSV、DuckDB 和模型二进制的干净 CI 环境仍可执行全部 Python 测试；真实数据全量构建继续留在本地验证链路。

看板使用 `.streamlit/config.toml` 和公共 Plotly 主题统一配色、留白、标题与比例轴，增长、商家、需求和行动筛选改为默认折叠。四张截图在 1440×1000 真实浏览器中重新生成并目视检查。首次截图发现百分比小值被舍入、页面残留滚动位置和组件尚未完全加载，随后改为两位百分比、等待骨架消失并强制滚动到顶部后复验。

岗位材料新增数据分析、增长分析、商业分析、电商运营分析四版，每版 5 条，所有数字来自统一证据包；真实业务手册将上线拆为 owner、数据契约、隐私、动作、实验和因果结果六类闸门，未满足时一律禁止宣称真实 ROI、增量成交或降低差评。自有代码许可证、远端 GitHub 仓库和公开部署仍需仓库所有者人工决定，不被伪造为已完成。

## 9. P14 托管 CI 数据隔离复验

首次公开推送后的 GitHub Actions run `30891909430` 暴露了本地验收缺口：5 个 mart 页面依赖本机 DuckDB，2 个行动/实验断言依赖本机 artifacts，导致托管 runner 的 Python 步骤有 7 项失败。Checkout、Python、依赖安装、仓库检查和 dbt parse 均通过，因此根因不是安装或 GitHub 权限。

P14 将主应用测试固定到不存在的数据库路径，验证无数据提示；10 个页面改用 `tests/streamlit_fixtures.py` 的微型合成输入验证页面字段和组件契约。设置 `OLIST_DB_PATH=/private/tmp/olist_ci_missing.duckdb` 后，本地 CI 等价命令实际为 64 项全部通过，作品集专项 17 项通过。合成 fixture 不改变本章任何真实业务数字，也不替代真实 dbt、模型和浏览器验证。最终 GitHub run 结果见 P14 日志。
