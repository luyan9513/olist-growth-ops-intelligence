# 干预记录与随机实验设计

## 1. P11 要解决的决策问题

P10 已经回答“本周优先关注哪些商家”，但离线名单覆盖不能回答“运营干预是否真的改善履约或经营结果”。P11 为真实运营补上测量闭环：在候选商家中预先登记实验、固定资格规则、随机分组、记录实际执行、等待结果成熟，再比较处理组与对照组。

当前 Olist 公开数据没有真实运营触达、执行成本或实验分组，因此本阶段只交付实验设计、数据契约、规划计算和代码验证。项目不生成虚构执行记录，不报告实验提升、显著性、ROI 或业务收益。

## 2. 建议的首个实验

| 项目 | 设计 |
|---|---|
| 决策 | 对高价值高风险商家提供一次标准化履约护航，是否降低后续低评分率或延迟率 |
| 使用者 | 商家运营负责人、履约运营、数据分析师 |
| 分组单位 | `seller_id`；同一商家只能进入一个组，避免商家内订单相互污染 |
| 候选池 | P10 行动快照中的 P1 履约护航商家；资格只使用分组前已知字段 |
| 处理组 | 接受事先定义、可核验的履约护航动作 |
| 对照组 | 维持既有运营流程，不额外执行该动作 |
| 主指标 | 结果窗内低评分订单数 / 合法评价订单数 |
| 次指标 | 延迟订单数 / 可判断延迟的已交付订单数 |
| 护栏 | 取消率、退款金额、单商家干预成本、评价覆盖率 |
| 观察窗 | 在实验登记表中预先填写；处理后才开始，必须等待评价和履约标签成熟 |
| 统计口径 | 意向处理（ITT）为主，即按最初随机组比较；实际执行率作为过程指标，不按是否执行重新分组 |

若现实运营更关心增长，可另建独立实验检验 P2 增长承接动作，主指标可换成商家活跃率或订单率。不同业务目标不得共用一个模糊的“综合收益”指标。

## 3. 实验生命周期

1. **登记**：在 `experiment_registry.csv` 中冻结假设、资格、主指标、护栏、显著性水平、把握度、时间窗和版本；
2. **资格快照**：从某一版 P10 行动清单筛选候选商家，保存快照日期和规则版本；
3. **随机分组**：使用 `experiment_id + seller_id + assignment_version` 生成稳定哈希，仅使用干预前分层字段；
4. **执行记录**：运营动作实际发生后写入执行日志；未执行、拒绝、失败也要保留状态；
5. **结果成熟**：统一观察窗结束后写入订单、履约、评价和成本的分子与分母；
6. **分析**：先做样本流失、分组平衡、执行率和指标成熟度检查，再做 ITT 比较；
7. **发布**：同时报告绝对差、相对差、置信区间、分母、缺失率、护栏和局限。未完成随机实验前不得使用因果措辞。

## 4. 随机化方案

### 4.1 稳定哈希

实现对每个唯一 `seller_id` 计算 SHA-256 哈希，输入包含实验 ID 和分组版本，映射到 `[0, 1)`。哈希值小于处理组比例时进入处理组，否则进入对照组。相同输入重复运行结果一致；改变实验 ID 或版本会产生新的随机序列。

该方案便于复现和审计，也不会依赖 DataFrame 当前行序。它不能替代分组发布前的平衡检查；小样本下仍可能不平衡。

### 4.2 分层字段

建议至少检查 `recommended_action`、`activity_band` 和 `seller_state`。这些字段都来自资格快照且早于干预。不得使用后续实际执行状态、后续订单、最终延迟、最终评价或退款结果做分层或重新分组。

### 4.3 防污染

- 同一实验中 `seller_id` 唯一；
- 分组一旦发布不可覆盖，修订必须增加新版本并保留旧快照；
- 同期互斥实验应在登记表中声明，避免同一商家同时接受冲突动作；
- 运营人员可看到执行清单，但不能手工把“更有希望”的商家移入处理组。

## 5. 样本量和 MDE 规划

页面使用两个独立比例的正态近似，输入基线率、希望识别的绝对变化、变化方向（风险降低或增长提高）、显著性水平、把握度和处理组比例，输出规划所需样本量。默认双侧检验，公式只用于实验前可行性规划；非 50/50 分流使用相对 50/50 的近似效率修正。

关键限制：

- 基线率必须来自同口径、足够近期且标签已成熟的历史数据；公开 Olist 样本只能做作品集演示，不能直接作为现实业务基线；
- MDE 是“希望实验有能力识别的最小绝对变化”，不是预测效果；
- 公式没有自动处理商家内多订单相关性、重复查看结果、多重指标、流失或不执行，应在真实上线时加入设计效应和样本膨胀；
- 若主指标分母是“有合法评价订单”，应按最终可评价商家/订单数规划，而不是按入组总数直接替代。

## 6. 四张日志表的数据契约

模板位于 `data/templates/experiment/`，只有表头，不包含虚构记录。

### 6.1 实验登记表

一行一个 `experiment_id`。必填假设、责任人、资格规则、处理/对照定义、主指标、护栏、计划时间、时区、alpha、power、状态和设计版本。状态建议只使用 `draft`、`approved`、`running`、`completed`、`cancelled`。

### 6.2 分组日志

一行一个 `assignment_id`，同一实验内 `seller_id` 唯一。保存资格快照日期、分层、行动类型、活动档位、哈希值和设计版本。分组日志是不可变事实表，不用后续结果覆盖。

### 6.3 执行日志

一行一次执行尝试，允许同一分组多次尝试。`assignment_id` 必须连接已有分组；记录执行时间、状态、动作类型、去标识化操作人、成本和结构化备注码。不要写自由文本中的姓名、电话或聊天内容。

### 6.4 结果日志

一行一个“分组 × 观察窗”结果。保存订单、已交付、延迟、评价、低评分、GMV、取消和退款的分子/分母，以及观察时间。必须满足：低评分数不超过评价数、延迟数不超过已交付数、取消数不超过订单数，结果窗结束不早于开始。

## 7. 分析前质量门槛

- 登记、分组、执行、结果可以沿主键完整追溯；
- 同一实验内商家不重复分组，分组值只包含 treatment/control；
- 分组时间不晚于首次执行时间，结果窗不早于分组和执行；
- 分组前字段的处理/对照分布被检查并披露，不因不平衡事后删样本；
- 各组资格数、执行数、结果成熟数和分母缺失数都单独报告；
- 主指标分子不大于分母，金额和计数不为负；
- 分析代码明确区分 ITT 与按方案执行分析，主结论以 ITT 为准；
- 未达到预先样本量或观察窗未成熟时，只报告进度，不下效果结论。

## 8. 当前可验证与不可验证内容

当前可以验证：样本量/MDE 计算边界、哈希分组的确定性和行序无关性、主键唯一、字段集合、时间顺序、分子分母关系、看板在真实 P10 候选池上的规划展示。

当前不能验证：实际执行率、真实成本、真实低评分/延迟增量、统计显著性、实验 ROI、跨期污染和现实运营可执行性。这些必须等真实日志接入后再评估。
