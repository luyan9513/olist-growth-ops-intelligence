## 2. 实现内容与原因

- 采用“先口径和粒度、后模型和页面”的顺序，因为订单商品、支付和评价直接连接存在多对多放大风险；
- 选 DuckDB + dbt-duckdb 作为本地分析栈，因为项目是公开样本的单机分析，能用较少基础设施实现 SQL 分层、测试和血缘；
- 将线索、低评分和需求预测分别定义预测时点与禁止字段，因为仅写“防泄漏”不足以形成可测试边界；
- 将历史情景模拟与真实 ROI/增量效果明确分开，因为数据不含真实成本和随机实验；
- 暂不设业务提升目标或填写模型指标，因为原始数据与运行环境尚未准备，任何数值都会是虚构。

本阶段没有真实 CSV、DuckDB mart 或模型产物，因此以下问题都不能在本阶段给出数字答案：

- 实际 MQL 数、有效成交数和成交率；

- 多评价、多商家订单、时间异常的真实规模；
- 三类模型是否超过基线、差距多大；
- 任何所谓“预计 ROI”或“业务提升”。

这些空白是有意保留的证据边界，不是遗漏。
