# P11 干预记录与随机实验框架开发日志

## 1. 阶段目标与完成边界

P10 已经把商家价值、增长、履约风险和下周活动概率转成 3,051 行可解释行动清单，但它只能回答“本周先关注谁”，不能回答“关注后是否真的改善了低评分、延迟或商家经营”。P11 的目标是补上从行动到因果验证之间的基础设施：实验登记、资格快照、随机分组、真实执行日志、成熟结果日志、样本量规划和实验设计页面。

本阶段的完成定义是“实验可以被正确规划、记录、校验和审计”，不是“实验已经完成”。Olist 公开数据没有运营人员触达、动作执行、成本或随机组别，因此本阶段绝不生成示例业务行，不计算处理效应、显著性、置信区间或 ROI，也不把草案组别描述成真实实验。

主要使用者是假设的商家运营负责人、履约运营负责人和数据分析师。首个建议用例是：在 P1 履约护航候选池中，以商家为单位随机分配标准化护航动作和既有流程，检验后续低评分率是否下降，并用延迟率、取消率、退款和成本做护栏。

## 3. 开发前固定的实验设计

### 3.1 为什么以商家而不是订单分组

P1 是商家级履约护航动作。若同一商家的部分订单进入处理组、部分进入对照组，运营动作很可能同时影响该商家的多个订单，造成组间污染。因此固定 `seller_id` 为分组单位，同一实验内一个商家只能出现一次。订单仍是低评分、延迟和取消指标的分子/分母，但不是随机化单位。

### 3.2 为什么用稳定哈希而不是每次随机抽样

普通随机抽样若没有保存随机状态，重复运行可能改变组别；DataFrame 行序变化也可能使分组难以审计。P11 固定用 `experiment_id + seller_id + assignment_version` 计算 SHA-256，再映射到 `[0, 1)`。相同实验、商家和版本重复运行结果一致，且不依赖输入行序。

稳定哈希不会自动保证小样本恰好 50/50，也不会保证州或活动档位完全平衡。因此页面必须同时展示组别数量和干预前维度分布；不能反复更换实验 ID，直到得到“好看”的平衡结果。

### 3.3 允许和禁止的分层字段

允许字段限定为 P10 资格快照中干预前已知的 `recommended_action`、`activity_band`、`seller_state`、`resource_segment` 和 `seller_segment`。代码会拒绝未批准字段。最终评价、最终延迟、后续订单、执行成功状态和后续成本都不能用于分层或重分组。

### 3.4 主分析和过程指标

主分析固定为意向处理（ITT）：按最初随机组比较，不因处理组实际未执行就删除，也不把对照组的其他自然接触重新归到处理组。实际执行率、拒绝率和成本是过程指标，用于解释可执行性，不替代 ITT 主结论。

### 3.5 样本量方法

实现使用两个独立比例的双侧正态近似，输入基线率、绝对 MDE、风险降低/增长提高方向、alpha、power 和处理组比例。50/50 使用标准近似；非均匀分流使用相对 50/50 的效率修正。它只用于实验前可行性，不自动处理商家内多订单相关性、标签成熟、无评价、未执行、多重检验或中途查看。

## 5. 核心代码实现

### 5.1 新增 `src/experiments.py`

该模块与 Streamlit 解耦，主要包含四类能力。

第一类是 `binary_proportion_sample_size`：验证基线率、MDE、alpha、power、分流比例和方向，计算处理组、对照组和总样本。返回值同时保存备择率，避免页面只显示一个没有方向的 MDE。

第二类是 `binary_proportion_mde`：给定当前候选量，用二分搜索反解同一公式下可检测的最小绝对变化。少于 4 个样本、基线越界或方向非法时拒绝计算。

第三类是 `assign_sellers` 和 `assignment_balance`：验证唯一非空商家、批准的干预前分层字段、资格快照和分组时间；按稳定哈希输出草案分组；再按活动档位和州汇总处理/对照数量与组内占比。输出含 `assignment_hash` 和 `design_version`，便于真实发布时保存证据。

第四类是 `validate_experiment_logs`：校验四张真实日志的字段、主键、连接、枚举、时间顺序、非负金额、币种、整数计数和分子分母关系。具体拒绝条件包括：

- 实验 ID重复、状态非法、alpha/power 非数值或越界、分组单位不是 `seller_id`；
- 同一实验商家重复、非法 treatment/control、分组早于资格快照、分组连接未登记实验；
- 执行记录无法连接分组，实验/商家/组别与分组不一致，执行早于分组，成本为负或非零成本缺少币种；
- 结果观察窗重复、无法连接分组、结果窗早于分组、观察时间早于窗口结束；
- 订单计数为负或非整数，已交付超过订单、延迟超过已交付、评价超过订单、低评分超过评价、取消超过订单。

该函数返回各表行数，只证明结构和链路通过，不计算实验效果。

### 5.2 新增 `tests/test_experiments.py`

最终新增 10 个测试函数，其中参数化非法样本输入展开为多个用例。覆盖：

3. 风险降低与增长提高得到正确备择率；

8. 最终评价等未批准分层字段被拒绝；
9. 干预前维度的处理/对照组内占比可对账到 100%；
10. 一条完整登记→分组→执行→结果链路通过，低评分分子超过评价分母和非整数订单数被拒绝；四张模板读入后均为 0 行。

## 7. 真实候选池规划结果

默认页面使用 P1 履约护航的 158 个唯一商家，规划参数为：

- 基线低评分率假设：14.19%；
- 目标方向：降低；
- 绝对 MDE：3 个百分点，即备择率 11.19%；
- 双侧 alpha：0.05；
- power：80%；
- 分流：处理/对照各 50%。

最终公式输出：处理组所需 1,932、对照组所需 1,932，总计 3,864 个成熟样本。用当前 158 个候选反解，可检测的下降约为 12.09897 个百分点，页面展示为 12.10%。这意味着在同一近似下，实验只能区分从 14.19% 降到约 2.09% 这样非常大的变化。

业务判断：单周 P1 池不能支持 3 个百分点的精细效果检验。真实团队应优先考虑跨周滚动入组并防止商家重复、等待统一结果成熟窗，或者预先扩大仍能接受同一标准化护航动作的资格池。不能在 158 个样本上得到不显著结果后写“干预无效”。

默认草案 `draft_p11_fulfillment_guard_v1` 的稳定哈希分组为处理组 82、对照组 76。活动档位：处理组高 64、中 18；对照组高 58、中 18。该不完全 50/50 是哈希阈值在小样本上的正常结果，未人工调整，也未更换实验 ID来追求平衡。

## 8. 实际遇到的问题、定位和处理

### 8.1 文档补丁上下文不匹配

第一次同时修改架构、数据设计和实验设计文档时，补丁期望找到“限制：不是高并发生产 BI”这句话，但原文实际是“取舍：不是生产级 BI 权限系统”。`apply_patch` 因上下文不一致拒绝整个补丁，没有产生半截修改。

处理方式是先用 `sed` 读取三个文件的精确段落，再按实际文本拆分并重放补丁。没有用全文件覆盖，也没有改动无关段落。

### 8.2 第一个样本量实现默认使用“提高”方向

初版函数把绝对 MDE直接加到基线率。它对增长率提高是合理输入，但首个履约实验目标是降低低评分率。初步手工输出为总样本 4,614、当前池可检测 MDE 18.78 个百分点；这不是代码崩溃，而是业务方向口径不完整。

在实际页面启动前复核时发现问题。修复方式是给样本量和 MDE 函数增加显式 `direction`，只允许 `decrease` 或 `increase`；页面增加“降低（风险指标）/提高（增长指标）”选择；测试同时断言 15% 基线降低 5 个百分点得到 10% 备择率、提高得到 20%。修正后最终权威值为总样本 3,864、当前池可检测下降 12.10 个百分点。初版数字没有写入最终报告。

### 8.3 并行运行 pytest 与 dbt 导致 DuckDB 文件锁冲突

为缩短验证时间，第一次全量验证同时启动 `.venv/bin/python -m pytest -q` 和 `make dbt-build`。dbt 对 `data/processed/olist.duckdb` 持有写锁，而 Streamlit 页面测试需要只读连接同一文件。结果 Python 测试出现 6 个失败，异常明确指出锁由 dbt Python 进程持有；纯 P11 公式、分组和页面测试没有失败。dbt 本身正常完成。

这是 DuckDB 单文件读写并发限制，不是 mart 或 P11 逻辑错误。没有修改 `app/data.py` 重试或复制数据库来掩盖问题。等 dbt 退出释放锁后，串行重跑全量 pytest，58 项全部通过。后续验收顺序固定为 dbt 完成后再运行读库页面测试。

### 8.4 Streamlit 端口在沙箱内无绑定权限

第一次运行 `.venv/bin/streamlit run app/app.py --server.headless true --server.port 8766` 时，系统在 socket bind 返回 `PermissionError: [Errno 1] Operation not permitted`。这是执行沙箱端口限制，不是应用异常。

按权限流程获得临时本机端口授权后，用同一命令启动；Uvicorn 成功监听 8766。随后访问 `http://localhost:8766/_stcore/health` 返回 `ok`，再发送 Ctrl-C停止服务。启动信息提示可选 Watchdog 未安装；该依赖只影响开发热更新性能，不影响当前运行，因此没有安装新依赖。

### 8.5 代码复核补强日志边界

日志校验初版已检查范围，但进一步审阅发现 `alpha`/`power` 的非数值可能在比较时变成 NaN并绕过单纯的大小判断；结果订单计数也应拒绝小数，非零成本应要求币种。修复后显式检查 NaN、整数计数、非零成本币种、观察窗唯一性和 `assignment_unit=seller_id`，并增加非整数订单测试。该问题在真实日志接入前被单测覆盖，没有造成已发布错误结果。

所有上述问题均已解决，本阶段未留下阻塞问题。

## 11. 仍存在的局限、风险和下一步

1. 样本量是独立比例近似，没有商家内订单聚类设计效应；真实统计设计应由历史成熟日志估计方差并膨胀样本；
2. 当前 P1 只有单周 158 个候选，跨周滚动时同一商家可能重复，必须使用实验级去重和冷却期；
3. 低评分主指标依赖合法评价，处理/对照评价覆盖不同会引入解释风险；结果成熟率和评价覆盖率必须先于效果结论；
4. 真实动作尚未标准化。若运营人员对不同商家做完全不同的动作，即使随机化成立，也难以解释“处理”具体是什么；
5. 稳定哈希是草案随机化机制，不替代实验审批、分层方案冻结、访问控制和不可变日志存储；
6. 模板当前是 CSV 契约，不是生产事件系统；真实接入需要受控数据库、权限、审计、时区和重试/幂等设计；
7. 没有渠道成本、毛利或完整退款数据，未来即使得到低评分变化，也不能自动推出利润或 ROI；
8. 下一阶段最有价值的工作不是继续调静态模型，而是由业务方确认标准化 P1 动作、平均工时、跨周资格、观察窗和成熟规则，再接入第一批真实日志。
